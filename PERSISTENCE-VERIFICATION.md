# Progress save: current evidence and limits

## Existing supported lifecycle (no cloud save added)
- `src/logic.ts`: SAVE_KEY `grind-district-save-v1`; Save v1 and `hydrate` whitelist/sanitize the existing fields. CV/resume/portfolio are derived by `documents(save)`, not a separate database document.
- `src/state.ts`: signup, successful/failed course submission, XP/rewards, inventory changes, settings and gameplay actions serialize the whole save immediately. Market state also autosaves after >5 seconds of ticking. `rememberPlace` persists meaningful (>~0.35m) position changes.
- `src/main.ts`: position checkpoint runs after >2 seconds; both that checkpoint and presence use `roomSession.cityPosition(pos)`. Indoor coordinates never become street save/presence coordinates. Reload starts outside at the last saved street position, not back inside. Latest movement before the next checkpoint can be lost; no page-close flush is claimed.
- `src/flat.ts`: overhead fallback also checkpoints street coordinates. No indoor state/schema was added.
- `src/state.ts attachPrivy`: first local guest-to-Privy association retains earned progress; repeat same ID is allowed, different/invalid ID is rejected before writing. This is a browser-profile association, NOT secure per-account storage or multiple local account slots. Signing out deliberately leaves the save. Another guest on the same browser sees the same local profile; localStorage can be edited. No credentials or auth tokens were added to saves.
- `src/net.ts`: Supabase realtime presence/positions are ephemeral, not save persistence. `server/verify-session.ts` verifies Privy access tokens; `api/privy/session.ts` returns identity, no durable gameplay writes. Course events are local and separate from save data. No actual DB records were queried.

## Verified defect fixed narrowly
Previously load failures fell back to a blank save and immediately persisted it. Malformed JSON, inaccessible reads and unsupported versions could therefore replace recoverable data; subsequent autosaves could do so too. Also removed a redundant second hydration when entering WebGL after onboarding: re-reading stale/absent storage discarded fresh in-memory identity when its write failed. Startup contract now enforces one hydration before onboarding; entry uses that live state. Load now protects the original by pausing writes for the session when data is unreadable/unsupported. No data migration, alternate save key or automatic account overwrite. Reload after storage/data recovery retries loading. Failed writes retain in-memory progress and previous durable data; a later successful normal write can retry the complete session state. Settings reports local-only, refused-write, or protected-save status when opened. There is no recovery/export UI and no promise to recover already overwritten data. Protected sessions cannot save until a valid/absent save can be loaded successfully.

## Automated acceptance
`src/persistence.check.ts` uses in-memory Storage with real state/course/inventory/room APIs: earned Spot course/CV/XP, owned/equipped drone, allowed mask/tint, practice ledger/preferences/activity recovery, no duplicated XP after load, indoor street-return checkpoint, guest association retention, same-account acceptance, rejected different account unchanged byte-for-byte, refused write then retry, refused read, corrupt JSON/null/array/missing version/future v2 preserved across mutations/autosave. No browser automation, device reload or real Privy/multiplayer round trip tested. Existing room tests separately cover exit clearances/navigation.

## Important origin boundary
localStorage is browser + origin specific. A new unique Vercel preview URL has a different save than the previous preview URL; it is not evidence that a same-origin reload failed. Use the stable preview branch alias consistently for browser save/reload acceptance:
https://grind-district-git-fix-gdd-six-preview-zahra-projects.vercel.app
Different device/browser, cleared site data, private/incognito storage, different domains and independent tabs are NOT a reliable cloud/account save. Concurrent tabs remain last-writer-wins; no synchronization/conflict protocol added.

## Minimum account-backed save proposal — separate review, NOT implemented
Reuse `verifyPrivySession` on each save GET/PUT request, not just a prior login response. Derive owner solely from verified claims, never the browser's privyId/account field. Store a validated, size-bounded gameplay-only v1 snapshot plus revision/update time under that owner in a private, unexposed Supabase schema. No browser table grants, RLS defense in depth, server-only least-privilege DB access; no secret/service key shipped to clients. If a privileged server key bypasses RLS, explicit verified-owner query constraints remain mandatory; prefer a narrowly permissioned server role with tested owner policies. Privy IDs are not automatically Supabase `auth.uid()` identities. Do not invent a JWT mapping.

Use optimistic revision checks and explicit guest-import/conflict review: never silently overwrite an existing cloud account with local guest state, another account, or a stale tab/device. Keep local pending changes through outages and show sync status; define sign-out/account-switch isolation before rollout. Reject malformed/unsupported payloads without destroying server data. Do not accept wallet/auth/financial authority from gameplay snapshots; existing client-earned XP is not tamper-proof certification. Test unauthenticated/expired tokens, cross-owner reads/writes, extra fields, duplicates, stale revisions, offline retry, guest import/conflict and deletion/retention before enabling. Gameplay snapshots restore progress; separate minimal aggregate statistics measure usage and cannot restore inventory/CV. No event/user telemetry or SQL/migrations were added here.

Reviewed current RLS guidance: https://supabase.com/docs/guides/database/postgres/row-level-security
